# Updater signing and release hosting

Contract for U2-P7-03 (#255): how updater packages are signed and verified, where the private key lives, how release assets and the manifest are named, and what happens when a key must change. The update check itself is in [Updater](UPDATER.md); packaging and the manual bootstrap from `v1.0.0-beta.1` are in [Updater compatibility](UPDATER_COMPATIBILITY.md). Publishing the manifest is #259.

**Two different signatures.** Tauri updater signatures (minisign) prove that a package came from the owner, and the app checks them before installing anything. Apple Developer ID signing and notarization, and Windows Authenticode, decide what the operating system shows the user. They are separate. The beta's unsigned installers ([Release](RELEASE.md)) do not waive updater signatures: every updater package is signed, and an unsigned or wrongly signed package is never installed.

| Private key    | Generated by the owner on their own Mac with `npx tauri signer generate -w ~/.tauri/unhollowed2-updater.key` (2026-11-19). Password-protected. It never entered this repository or this conversation.        |

### Custody (owner)

1. Keep `~/.tauri/unhollowed2-updater.key` and its password in **two separate places**: the password in a password manager, and an encrypted offline copy of the key file (for example, an encrypted disk image on removable storage). Losing either one means losing the key.
2. Never commit, paste, email, or upload the key file or its password. `scripts/verify-artifacts.sh` fails any release folder that contains a private key, in plain text or in base64.
3. Only two places hold a working copy: the owner's Mac and the `updater-signing` GitHub environment.

### GitHub environment (owner, once, before the next release tag)

Create an environment named **`updater-signing`** (Settings → Environments). Give it:

- **Required reviewers:** the owner. Every signing run then waits for approval.
- **Deployment branches and tags:** selected only: tags `v*` and the branch `main`.
- **Secrets:** `TAURI_SIGNING_PRIVATE_KEY` (the key file's contents) and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. From the project folder, so nothing is echoed:

```bash
gh secret set TAURI_SIGNING_PRIVATE_KEY --env updater-signing < ~/.tauri/unhollowed2-updater.key
```

```bash
gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD --env updater-signing
```

The second command prompts for the password. Use no repository-level or organization-level copy of these secrets.

### When CI signs

`Desktop packaging` (`.github/workflows/platform-build.yml`) signs only on a `v*` tag push or when started by hand with **updater** checked. Only those runs enter the `updater-signing` environment, so only they can read the secrets. A missing secret fails the run before the build. Ordinary pushes and validation runs build unsigned packages with `--no-sign`, exactly as before.

A signing run adds `--config src-tauri/tauri.updater.conf.json`, which turns on `bundle.createUpdaterArtifacts`, and drops `--no-sign`: that flag also skips updater signatures (found in the local trial below). Without Apple or Windows certificates, the installers stay unsigned by the operating system either way.

`scripts/verify-artifacts.sh <platform> <folder> <version> updater` then requires every package and `.sig`, and checks each signature's trusted comment for `version:<version>` and its key ID against the embedded public key. Tauri only _warns_ about a key mismatch, so this check is the one that stops it. GitHub masks secret values in logs. The signed files hold only signatures and public data.

### Local signing (owner, only if CI is unavailable)

```bash
export TAURI_SIGNING_PRIVATE_KEY_PATH=~/.tauri/unhollowed2-updater.key
```

```bash
read -rs TAURI_SIGNING_PRIVATE_KEY_PASSWORD && export TAURI_SIGNING_PRIVATE_KEY_PASSWORD
```

```bash
npx tauri build --ci --bundles app,dmg --config src-tauri/tauri.updater.conf.json -- --locked
```

Then stage and verify the files as the workflow does, and close the terminal so the password leaves memory. Prefer CI, which builds from the reviewed tag.

## Assets and manifest

### Platform mapping

| Manifest key          | Package (release asset)                     | Built from                                      |
| --------------------- | ------------------------------------------- | ----------------------------------------------- |
| `darwin-aarch64`      | `Unhollowed-2_<version>_aarch64.app.tar.gz` | `bundle/macos/Unhollowed 2.app.tar.gz`, renamed |
| `darwin-aarch64-app`  | the same                                    |                                                 |
| `windows-x86_64-nsis` | `Unhollowed-2_<version>_x64-setup.exe`      | `bundle/nsis/`                                  |
| `windows-x86_64-msi`  | `Unhollowed-2_<version>_x64_en-US.msi`      | `bundle/msi/`                                   |
| `windows-x86_64`      | the NSIS setup (fallback key)               |                                                 |

Each package has a `<package>.sig` next to it. The app asks for `{os}-{arch}-{installer}` first and falls back to `{os}-{arch}`. The installer-specific keys keep an MSI install on MSI updates and an NSIS install on NSIS updates (W-2 in [Updater compatibility](UPDATER_COMPATIBILITY.md)). Intel Macs, Windows ARM64, and Linux have no entry: the app reports them as unsupported without contacting the feed. Staged files use the product name with a space (`Unhollowed 2_…`). Release assets replace the space with a hyphen, as the `v1.0.0-beta.1` assets do.

### Manifest

`node scripts/updater-manifest.mjs <folder> <version> [notes-file]` prints `latest.json` in Tauri's static format: `version`, `notes`, `pub_date`, and a `platforms` entry with `url` and `signature` for each key above. URLs point at the versioned release, `https://github.com/arlecchinoOPSource/Unhollowed-2/releases/download/v<version>/<asset>`. The script prints nothing and fails if any package or signature is missing, if a signature is bound to another version, or if it was made by another key.

### Feed ownership

The beta feed is the asset `latest.json` on a dedicated release tagged `updater-beta` in this repository. The owner controls it. Only the approved publish step in #259 replaces it, and it does so last, after the versioned release and its assets are public. Nothing in this change creates or changes a release.

## Key rotation, compromise, and loss

The app trusts exactly one public key. A new key reaches users only inside an update signed by the **old** key.

| Situation            | What to do                                                                                                                                                                                                                                                                                                                  |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Planned rotation     | Generate a new key. Ship one release whose app embeds the **new** public key but whose packages are signed with the **old** key. Update the key ID in `securityConfig.test.tsx` in the same PR. After users take that release, sign with the new key and replace the environment secrets. Keep the old key until then.      |
| Suspected compromise | Delete both secrets from `updater-signing`. An attacker also needs to change the feed, which needs repository access, so review repository access and the `updater-beta` release at once. Then do the rotation above as soon as possible. Until it ships, installed apps still trust the old key.                           |
| Lost key or password | Installed apps cannot accept any new update. Generate a new key, ship a release with the new public key, and ask every user to install it **by hand**, as the first updater-enabled build was ([manual bootstrap](UPDATER_COMPATIBILITY.md#manual-bootstrap-from-v100-beta1)). The custody steps above exist to avoid this. |

A failed or missing download changes nothing: the plugin verifies the bytes before `install` touches the installed app, and the check and the download never modify the workspace. There is no automatic rollback; installation safety is #258.
